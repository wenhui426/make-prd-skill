# 文档结构完整性检查

> Supporting reference for the `make-prd` skill（STEP 3 质量审查）。在执行文档结构完整性检查时加载；单独使用时请先提供待检查的 PRD 内容。审查对象：全文结构，按 make-prd 的 8 核心章 + 4 可选章结构核对。

## 维度说明

PRD文档的结构完整性直接影响评审效率和开发交付质量。一份结构清晰、章节完整的PRD能降低沟通成本、减少需求遗漏。make-prd 采用裁剪后的结构：原《决胜B端PRD模板v2.0》14 章节合并为 8 核心章 + 4 可选章（A 项目风险/B 术语/C 参考文献/D 运营计划），可选章由用户确认后启用。

**核心理论框架：**

1. **make-prd 标准文档结构**（8 核心章）：1 项目背景与基本情况（原1+2合并）→ 2 目标与收益（原3+4合并）→ 3 方案概述（原5）→ 4 范围与MVP（原6）→ 5 功能需求（原10，含模块规划/框架概述/逐模块详情/异常处理）→ 6 数据埋点（原11）→ 7 角色与权限（原12）→ 8 待决事项（原14）；可选 A 项目风险（原7）、B 术语（原8）、C 参考文献（原9）、D 运营计划（原13）。

2. **文档版本管理**：PRD交付前必须标记版本号，每次修改在头部修改记录表追加记录（时间/变更单元/动作/评审状态），只追加不改写。

3. **功能描述五种规则类型**：事实、约束、触发条件、推论、计算——功能规则描述必须归类到这五种类型之一，确保无遗漏。

4. **自顶向下的设计思路**（《决胜B端》第2章）：B端产品总体建设遵循"从抽象到具体"的原则，PRD文档结构应体现这一思路。

## 检查清单

### 11.1 文档元信息

- [ ] **文档头部信息完整性**
  - 检查内容：PRD是否包含文档信息表头（产品名/迭代版本号/负责人/来源定型稿/日期/状态）
  - 优质标准：所有字段已填写；迭代版本号与文件名一致、与 01-产品规划 贯穿一致；来源定型稿指向具体的 01-产品规划 文档
  - 问题标志：元信息缺失或填写不完整（如负责人写"待定"）；版本号与文件名不一致
  - 参考依据：make-prd 文档信息表头格式（见 [assets/02-PRD模板.md](../../assets/02-PRD模板.md)）

- [ ] **修改记录表维护**
  - 检查内容：是否维护了完整的修改记录表
  - 优质标准：每次修改都追加一条记录（时间/变更单元/动作/评审状态），只追加不改写；记录与文档实际变更能对应上
  - 问题标志：无修改记录，或修改后未追加记录，或改写旧记录
  - 参考依据：make-prd STEP 2 修改记录纪律——"对 PRD 的任何修改都在头部修改记录表追加一条记录"

### 11.2 核心章节完整性（第1-8章）

- [ ] **第1章 项目背景与基本情况**
  - 检查内容：是否包含项目背景（业务现状、面临问题、解决思路，有数据支持）+ 需求基本情况（需求提出人/功能使用人/受影响人、场景六要素、发生频率、核心痛点、需求价值）
  - 问题标志：背景空泛或缺失；多个要素字段缺失
  - 参考依据：新第1章为原第1+2章合并

- [ ] **第2章 目标与收益**
  - 检查内容：是否包含产品定位/商业分析（商业化产品：目标市场与客户分析+竞品分析；自研：同类系统调研+痛点优先级）+ 符合SMART原则的量化目标（验收与成功标准、收益预期），承接产品规划的**实现价值**（用户价值/业务价值/商业价值）
  - 问题标志：商业分析缺失或仅有空壳；目标模糊
  - 参考依据：新第2章为原第3+4章合并

- [ ] **第3章 方案概述**
  - 检查内容：是否用简要语言概述了核心功能或项目方案，并包含非功能需求（性能/安全/可用性等）
  - 问题标志：无概述直接进入细节；非功能需求缺失
  - 参考依据：新第3章含非功能需求

- [ ] **第4章 范围与MVP**
  - 检查内容：是否明确了本期范围（涉及的系统/产品/接口/影响范围）+ MVP 边界（本期做/暂缓/不做）+ 演进规划
  - 问题标志：范围不明确，后续开发时才发现遗漏的关联方
  - 参考依据：新第4章承接产品规划的范围边界

- [ ] **第6章 数据埋点**
  - 检查内容：是否按统一标准描述了需要监控的按钮、页面、事件
  - 优质标准：埋点设计覆盖核心操作路径，标注了事件名称、触发条件、采集参数
  - 问题标志：无埋点设计，或只有"后续补充"的占位符
  - 参考依据：新第6章（原第11章）

- [ ] **第7章 角色与权限**
  - 检查内容：是否以权限矩阵的形式描述了各角色在各页面/功能上的权限
  - 优质标准：用表格形式列出一级导航、页面、页面元素与各角色的权限对应关系，精确到按钮级别
  - 问题标志：权限描述模糊（如"管理员有所有权限"），未精确到页面元素级别
  - 参考依据：新第7章（原第12章）角色权限矩阵格式

- [ ] **第8章 待决事项**
  - 检查内容：是否明确列出了文档中结论待定的事项
  - 优质标准：待决事项按 D001 连续编号，有描述、来源、影响、负责人、阻塞级别（是否阻塞评审），数量不应过多（<10 项为宜）
  - 问题标志：明显有未决事项但未记录；待决事项数量过多说明PRD成熟度不够
  - 参考依据：新第8章（原第14章）D 编号规则与 [assets/02-PRD模板.md](../../assets/02-PRD模板.md) 一致

### 11.3 功能需求章节（第5章）

- [ ] **模块规划（5.1节）**
  - 检查内容：是否在功能详情之前提供了模块规划（模块清单/页面菜单功能覆盖/依赖图/建议开发顺序/可并行）
  - 问题标志：无模块规划直接进入功能详情
  - 参考依据：make-prd STEP 2 ④ 模块规划先行纪律

- [ ] **产品框架概述（5.2节）**
  - 检查内容：是否包含系统框架图、ER数据模型图、业务流程图、状态机图（按产品类型配置图集）
  - 优质标准：框架图层次清晰，数据模型用ER图表达，流程图用跨部门泳道图表达；图后附功能清单表格（子系统/页面/多端覆盖情况）
  - 问题标志：无任何框架概述图，直接进入页面级描述
  - 参考依据：新第5章 5.2 节与 [references/step2-prd/typing.md](../../references/step2-prd/typing.md) 图集规则

- [ ] **逐模块详情的规范性（5.3节）**
  - 检查内容：功能需求描述是否采用 7 段式结构化方式（功能目标/流程与页面交互/状态说明/业务规则/数据要求/验收标准AC编号/权限）
  - 优质标准：每个功能模块按 7 段式书写；列表页有查询条件表格、列表字段表格；规则描述按五种类型归类（事实/约束/触发条件/推论/计算）；验收标准有 AC 编号
  - 问题标志：功能描述为大段自然语言叙述，无结构化表格和分类；验收标准无编号
  - 参考依据：新第5章 5.3 节 7 段式（承袭 prd-make 执行纪律）

- [ ] **异常处理方案（5.4节）**
  - 检查内容：是否有专门的异常情况处理方案
  - 优质标准：覆盖断网、断电、误操作、数据丢失、并发冲突等异常场景，每种异常有处理方案
  - 问题标志：无异常处理章节，或仅提"参见后续补充"
  - 参考依据：新第5章 5.4 节

### 11.4 可选章节（A-D，按需启用）

- [ ] **可选章启用合规**
  - 检查内容：可选章是否按需启用，且启用后有实质内容
  - 优质标准：可选 A 项目风险（涉及多系统集成/合规/大投入时）、可选 B 术语（专业领域）、可选 C 参考文献（有引用来源）、可选 D 运营计划（商业化/需上线推广）——启用条件与 make-prd STEP 2 ⑦ 一致；未启用的章不占位
  - 问题标志：可选章启用但内容为空壳；或明显需要却未启用（如强监管行业无风险章）
  - 参考依据：make-prd STEP 2 ⑦ 可选章提示确认

## 常见问题诊断

| 问题现象 | 根本原因 | 改进方向 |
|---------|---------|---------|
| PRD只有功能描述，缺少背景和分析 | 把PRD当功能说明书写 | 按 8 核心章结构补充前置章节 |
| 功能描述是大段文字 | 不熟悉结构化描述方法 | 采用 7 段式 + 表格 + 规则分类的标准格式 |
| 无修改记录 | 缺乏文档管理意识 | 建立修改记录纪律，每次修改必追加 |
| 权限描述模糊 | 未做角色权限矩阵 | 按模板格式建立角色-页面-元素权限矩阵 |
| 待决事项过多 | PRD尚未成熟就匆忙评审 | 先解决核心待决事项再提交评审 |
| 缺少框架概述图 | 直接跳入细节设计 | 先完成系统框架图、ER图、流程图、状态机图 |
| 模块规划缺失 | 跳过规划直接写详情 | 先确认模块规划，再逐模块写功能详情 |
