## make-prd-ch04

# 第4章 范围与 MVP — 生成指引

> 生成 PRD 第4章"范围与 MVP"的指引文件。信息来自产品规划的"范围边界"，不重复收集。

## 章节目标

明确项目的 MVP 边界、暂缓范围和影响范围，提前识别关联方，避免遗漏和范围蔓延。

> 💡 B 端 MVP 原则：必须支撑核心业务流程闭环，不是"最简单的版本"

## 生成结构

```md
## 4、范围与 MVP

### 4.1 MVP 范围

**MVP 包含的功能：**
{列出 MVP 版本包含的功能及理由}

**MVP 暂不包含的功能：**
{列出延后的功能及延后理由}

**核心验证假设：**
1. {假设1：通过 MVP 要验证什么}
2. {假设2}

| 能力 | 包含行为 | 纳入原因 |
|------|----------|----------|
|      |          |          |

### 4.2 暂缓范围

| 暂缓项 | 暂缓原因 | 何时重新评估 |
|--------|----------|--------------|
|        |          |              |

### 4.3 涉及系统

| 系统名称 | 关系类型 | 影响描述 | 责任方 |
| --- | --- | --- | --- |
| {本系统} | 主体 | 新建/改造 | {产品团队} |

- **用户影响**：{哪些用户群体会受到影响}
```

## 生成规则

1. **MVP 范围**：从产品规划的"MVP 范围"和"场景优先级"提取；0-1 新产品必须明确 MVP 边界，迭代需求此节可简化。
2. **暂缓范围**：从产品规划的"暂缓范围"和"明确不做"提取。
3. **涉及系统**：从用户业务描述中推断可能涉及的系统（如 CRM、ERP、OA、支付系统等）。
4. **不在本期范围内**很重要 — 明确边界比扩大范围更有价值。
5. 信息不足时，至少列出"本系统"行，其他标注 `[TODO: 请梳理与哪些系统有数据交互]`。

## 质量标准

- [ ] MVP 范围能支撑核心业务闭环
- [ ] 暂缓项有暂缓原因和重新评估时机
- [ ] 所有涉及系统都已列出，含责任方
- [ ] 影响范围覆盖用户、流程、数据三个维度
- [ ] 有明确的"不在范围内"清单
