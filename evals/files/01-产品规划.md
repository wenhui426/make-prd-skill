# 业主报修小程序 产品规划

- 项目名：业主报修小程序
- 迭代版本号：1.2
- 日期：2026-08-10
- 状态：已冻结（定型稿）

## 1. 基本描述

- 原始需求：业主报修流程混乱，电话报修无法追踪，维修单靠纸质记录，业主不知道进度，反复打电话催。
- 一句话定位：面向业主的报修入口 + 面向物业工程部的维修工单闭环管理。
- 目标用户：业主（C 端）、物业客服、工程部维修工、项目经理。
- 约束：复用公司现有账号体系；业主端为微信小程序，物业端为 Web 管理后台。
- 迭代记录：v1.1 上线报修+工单闭环；v1.2 增加评价功能。

## 2. 实现价值

- 用户价值：业主随时报修、实时看到处理进度、修完可评价。
- 业务价值：报修全流程线上化，工单可追踪、可统计、可考核维修工。
- 商业价值：提升业主满意度、降低投诉率，为后续增值服务（家政、维修付费）打基础。

## 3. JTBD 场景

| 优先级 | 情境 | 动机 | 期望进展 |
|--------|------|------|---------|
| 高 | 业主发现家里漏水/灯坏 | 快速解决，不想打电话排队 | 拍照上报 → 看到接单 → 上门维修 → 确认完成 → 评价 |
| 中 | 老年业主不会用手机，打电话给客服 | 报修诉求被受理 | 客服代报修，生成工单 |
| 低 | 项目经理月度例会 | 了解维修效率与满意度 | 统计报表：接单时效、完成率、好评率 |

## 4. 范围边界

- 产品形态：微信小程序（业主端）+ Web 管理后台（物业端）。
- MVP 范围：报修上报、客服审核、工单分配、接单/完工、进度查看、评价。
- 暂缓范围：自动派单算法、物料库存管理、多小区管理、在线支付。
- 假设：与老工单系统通过接口单向同步工单状态（老系统只读）。

## 5. 页面流程

- 页面清单：业主端（首页、报修表单、工单详情、评价页）；物业端（工单列表、工单详情、分配工单、统计报表）。
- 主流程：业主提交报修 → 客服审核 → 维修工接单 → 上门维修 → 业主确认完成 → 评价。
- 状态流转：待审核 → 已派单 → 维修中 → 待确认 → 已完成 → 已评价；可作废（作废需注明原因）。
- 核心数据对象：业主、报修单、维修工、工单、评价。
- 权限：业主（仅自己工单）；客服（审核、派单）；维修工（接单、填报完工）；项目经理（全部 + 报表）。
